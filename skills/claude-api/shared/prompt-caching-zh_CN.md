# 提示缓存 — 设计与优化

本文件介绍如何设计提示构建代码以实现有效缓存。有关特定语言的语法，请参阅每种语言的 README 或单文件文档中的 `## 提示缓存` 部分。

## 一切遵循的一个不变量

**提示缓存是前缀匹配。前缀中任何位置的任何更改都会使其后的所有内容失效。**

缓存键是从渲染的提示到每个 `cache_control` 断点的精确字节派生的。位置 N 处的单字节差异 — 时间戳、重新排序的 JSON 键、列表中不同的工具 — 会使位置 ≥ N 处的所有断点的缓存失效。

渲染顺序是：`tools` → `system` → `messages`。最后一个系统块上的断点会同时缓存工具和系统。

围绕此约束设计提示构建路径。正确排序，大多数缓存就可以免费工作。弄错了，再多的 `cache_control` 标记也无济于事。

---

## 优化现有代码的工作流

当要求添加或优化缓存时：

1. **追踪提示组装路径。** 找出 `system`、`tools` 和 `messages` 的构建位置。识别流入它们的每个输入。
2. **按稳定性对每个输入分类：**
   - 从不改变 → 属于提示的早期部分，在任何断点之前
   - 每个会话改变 → 属于全局前缀之后，按会话缓存
   - 每轮改变 → 属于最后，在最后一个断点之后
   - 每个请求改变（时间戳、UUID、随机 ID）→ **消除或移到最末尾**
3. **检查渲染顺序与稳定性顺序匹配。** 稳定内容必须在物理上先于易失内容。如果时间戳插入到系统提示标题中，无论标记如何，其后的所有内容都无法缓存。
4. **在稳定性边界处放置断点。** 请参阅下面的放置模式。
5. **审核静默失效器。** 请参阅反模式表。

## 放置模式

### 跨许多请求共享的大型系统提示

在最后一个系统文本块上放置断点。如果有工具，它们在系统之前渲染 — 最后一个系统块上的标记会一起缓存工具 + 系统。

```json
"system": [
  {"type": "text", "text": "<大型共享提示>", "cache_control": {"type": "ephemeral"}}
]
```

### 多轮对话

在最近追加的轮次的最后一个内容块上放置断点。每个后续请求都会重用整个先前的对话前缀。较早的断点仍然是有效的读取点，因此随着对话的增长，命中会逐步累积。

```json
// 最后一个用户轮次的最后一个内容块
messages[-1].content[-1].cache_control = {"type": "ephemeral"}
```

### 共享前缀，变化的后缀

许多请求共享大型固定前言（少量示例、检索到的文档、指令），但最终问题不同。将断点放在**共享**部分的末尾，而不是整个提示的末尾 — 否则每个请求都会写入一个不同的缓存条目，并且永远不会读取任何内容。

```json
"messages": [{"role": "user", "content": [
  {"type": "text", "text": "<共享上下文>", "cache_control": {"type": "ephemeral"}},
  {"type": "text", "text": "<变化的问题>"}  // 无标记 — 每次都不同
]}]
```

### 每次都从头开始改变的提示

不要缓存。如果前 1K 个令牌每个请求都不同，则没有可重用的前缀。添加 `cache_control` 只会支付缓存写入溢价而零读取。关掉它。

## 架构指导

这些是比标记放置更重要的决定。先修复这些。

**保持系统提示冻结。** 不要将"当前日期：X"、"模式：Y"、"用户名：Z"插入系统提示 — 它们位于前缀的前面，会使下游的所有内容失效。将动态上下文作为 `messages` 中稍后的用户或助手消息注入。第 5 轮的消息不会使第 5 轮之前的任何内容失效。

**不要在对话中途改变工具或模型。** 工具在位置 0 渲染；添加、移除或重新排序工具会使整个缓存失效。切换模型同样如此（缓存是模型范围的）。如果您需要"模式"，不要交换工具集 — 给 Claude 一个记录模式转换的工具，或将模式作为消息内容传递。确定性地序列化工具（按名称排序）。

**分支操作必须重用父级的精确前缀。** 侧计算（摘要、压缩、子智能体）经常启动单独的 API 调用。如果分支以任何差异重建 `system` / `tools` / `model`，它会完全错过父级的缓存。逐字复制父级的 `system`、`tools` 和 `model`，然后在末尾附加分支特定的内容。

## 静默失效器

在审查代码时，在任何输入到提示前缀的内容中 grep 查找这些：

| 模式 | 为什么它会破坏缓存 |
|---|---|
| 系统提示中的 `datetime.now()` / `Date.now()` / `time.time()` | 前缀每个请求都改变 |
| 内容早期的 `uuid4()` / `crypto.randomUUID()` / 请求 ID | 同样 — 每个请求都是唯一的 |
| 没有 `sort_keys=True` 的 `json.dumps(d)` / 迭代 `set` | 非确定性序列化 → 前缀字节不同 |
| f-string 将会话/用户 ID 插入系统提示 | 每用户前缀；无跨用户共享 |
| 条件系统部分（`if flag: system += ...`） | 每个标志组合都是不同的前缀 |
| `tools=build_tools(user)` 其中集合因用户而异 | 工具在位置 0 渲染；没有跨用户缓存 |

通过将动态片段移到最后一个断点之后，使其确定性，或者如果它不是负载承载的则删除它来修复。

## API 参考

```json
"cache_control": {"type": "ephemeral"}              // 5 分钟 TTL（默认）
"cache_control": {"type": "ephemeral", "ttl": "1h"} // 1 小时 TTL
```

- 每个请求最多 **4** 个 `cache_control` 断点。
- 可以放在任何内容块上：系统文本块、工具定义、消息内容块（`text`、`image`、`tool_use`、`tool_result`、`document`）。
- `messages.create()` 上的顶级 `cache_control` 自动放在最后一个可缓存块上 — 当您不需要细粒度放置时，这是最简单的选项。
- 最小可缓存前缀取决于模型。较短的前缀会静默地不会缓存，即使有标记 — 没有错误，只是 `cache_creation_input_tokens: 0`：

| 模型 | 最小值 |
|---|---:|
| Opus 4.8、Opus 4.7、Opus 4.6、Opus 4.5、Haiku 4.5 | 4096 令牌 |
| Sonnet 4.6、Haiku 3.5、Haiku 3 | 2048 令牌 |
| Sonnet 4.5、Sonnet 4.1、Sonnet 4、Sonnet 3.7 | 1024 令牌 |

一个 3K 令牌的提示在 Sonnet 4.5 上会缓存，但在 Opus 4.8 上会静默地不会缓存。

**经济性：** 缓存读取成本约为基础输入价格的 0.1 倍。缓存写入对于 5 分钟 TTL 成本为 **1.25 倍**，对于 1 小时 TTL 为 2 倍。盈亏平衡取决于 TTL：使用 5 分钟 TTL，两个请求达到盈亏平衡（1.25 倍 + 0.1 倍 = 1.35 倍对比 2 倍未缓存）；使用 1 小时 TTL，您至少需要三个请求（2 倍 + 0.2 倍 = 2.2 倍对比 3 倍未缓存）。1 小时 TTL 使条目在突发流量的间隙中保持活动状态，但翻倍的写入成本意味着它需要更多的读取才能获得回报。

## 验证缓存命中

响应 `usage` 对象报告缓存活动：

| 字段 | 含义 |
|---|---|
| `cache_creation_input_tokens` | 为此请求写入缓存的令牌（您支付了 ~1.25 倍的写入溢价） |
| `cache_read_input_tokens` | 为此请求从缓存提供服务的令牌（您支付了 ~0.1 倍） |
| `input_tokens` | 全价处理的令牌（未缓存） |

如果在具有相同前缀的重复请求中 `cache_read_input_tokens` 为零，则静默失效器在起作用 — 比较两个请求之间渲染的提示字节以找到它。

**`input_tokens` 只是未缓存的剩余部分。** 总提示大小 = `input_tokens + cache_creation_input_tokens + cache_read_input_tokens`。如果您的智能体运行了数小时但 `input_tokens` 显示为 4K，则其余部分是从缓存提供服务的 — 检查总和，而不是单个字段。

特定语言的访问：`response.usage.cache_read_input_tokens`（Python/TS/Ruby）、`$message->usage->cacheReadInputTokens`（PHP）、`resp.Usage.CacheReadInputTokens`（Go/C#）、`.usage().cacheReadInputTokens()`（Java）。

## 失效层次结构

并非每个参数更改都会使所有内容失效。API 有三个缓存层，更改只会使它们自己的层和下面的层失效：

| 更改 | 工具缓存 | 系统缓存 | 消息缓存 |
|---|:---:|:---:|:---:|
| 工具定义（添加/移除/重新排序） | ❌ | ❌ | ❌ |
| 模型切换 | ❌ | ❌ | ❌ |
| `speed`、网络搜索、引用切换 | ✅ | ❌ | ❌ |
| 系统提示内容 | ✅ | ❌ | ❌ |
| `tool_choice`、图像、`thinking` 启用/禁用 | ✅ | ✅ | ❌ |
| 消息内容 | ✅ | ✅ | ❌ |

含义：您可以每个请求更改 `tool_choice` 或切换 `thinking`，而不会丢失工具 + 系统缓存。不要过度担心这些 — 只有工具定义和模型更改才会强制完全重建。

---

## 20 块回溯窗口

每个断点向后**最多 20 个内容块**查找先前的缓存条目。如果单个轮次添加超过 20 个块（在具有许多 tool_use/tool_result 对的智能体循环中很常见），下一个请求的断点将找不到先前的缓存并静默错过。

修复：在长轮次中每 ~15 个块放置一个中间断点，或者将标记放在与上一轮最后一个缓存块相距 20 以内的块上。

---

## 并发请求时序

缓存条目只有在第一个响应**开始流式传输**之后才变得可读。具有相同前缀的 N 个并行请求都会支付全价 — 没有一个可以读取其他仍在写入的内容。

对于扇出模式：发送 1 个请求，等待第一个流式传输的令牌（不是完整响应），然后触发剩余的 N-1 个。它们将读取第一个刚刚写入的缓存。
