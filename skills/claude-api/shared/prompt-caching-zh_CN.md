# 提示缓存 —— 设计与优化

本文档介绍如何设计提示构建代码以实现高效的缓存。有关各语言的具体语法，请参阅各语言 README 或单文件文档中的 `## Prompt Caching` 部分。

## 一切遵循的唯一不变原则

**提示缓存是前缀匹配。前缀中任何位置的更改都会使其之后的所有内容失效。**

缓存键由渲染后的提示中每个 `cache_control` 断点之前的精确字节生成。位置 N 处的一个字节差异 —— 一个时间戳、一个重新排序的 JSON 键、列表中的不同工具 —— 会使位置 ≥ N 的所有断点的缓存失效。

渲染顺序是：`tools` → `system` → `messages`。最后一个系统块上的断点会将工具和系统一起缓存。

围绕这一约束设计提示构建路径。顺序正确，大多数缓存无需额外工作即可生效。顺序错误，再多的 `cache_control` 标记也无济于事。

---

## 优化现有代码的工作流程

当被要求添加或优化缓存时：

1. **追踪提示组装路径。** 找到 `system`、`tools` 和 `messages` 的构建位置。识别所有流入其中的输入。
2. **按稳定性对每个输入进行分类：**
   - 从不变化 → 位于提示的前部，在任何断点之前
   - 每次会话变化 → 位于全局前缀之后，按会话缓存
   - 每次轮次变化 → 位于末尾，在最后一个断点之后
   - 每次请求变化（时间戳、UUID、随机 ID）→ **消除或移到最末尾**
3. **检查渲染顺序是否与稳定性顺序一致。** 稳定内容必须在物理位置上先于易变内容。如果时间戳被插入了系统提示的头部，那么无论标记如何，其后所有内容都无法缓存。
4. **在稳定性边界放置断点。** 参见下面的放置模式。
5. **审查静默失效因素。** 参见反模式表。

## 放置模式

### 多个请求共享的大型系统提示

在最后一个系统文本块上放置断点。如果有工具，它们会在系统之前渲染 —— 最后一个系统块上的标记会将工具 + 系统一起缓存。

```json
"system": [
  {"type": "text", "text": "<large shared prompt>", "cache_control": {"type": "ephemeral"}}
]
```

### 多轮对话

在最近追加轮次的最后一个内容块上放置断点。每次后续请求都会重用之前的整个对话前缀。更早的断点仍然是有效的读取点，因此随着对话增长，命中会逐步累积。

```json
// 最后一个用户轮次的最后一个内容块
messages[-1].content[-1].cache_control = {"type": "ephemeral"}
```

### 共享前缀，变化后缀

许多请求共享一个大型固定前导部分（少样本示例、检索到的文档、指令），但最终问题各不相同。将断点放在**共享**部分的末尾，而不是整个提示的末尾 —— 否则每个请求都会写入不同的缓存条目，没有任何内容被读取。

```json
"messages": [{"role": "user", "content": [
  {"type": "text", "text": "<shared context>", "cache_control": {"type": "ephemeral"}},
  {"type": "text", "text": "<varying question>"}  // 无标记 —— 每次均不同
]}]
```

### 每次从头开始变化的提示

不要缓存。如果前 1K 令牌每个请求都不同，就没有可重用的前缀。添加 `cache_control` 只会支付缓存写入的开销而没有任何读取收益。保持不加标记。

## 架构指导

这些是比标记放置更重要的决策。先处理好这些。

**保持系统提示不变。** 不要将"当前日期：X"、"模式：Y"、"用户名：Z"插值到系统提示中 —— 它们位于前缀的前部，会使下游所有内容失效。将动态上下文作为用户或助手消息稍后在 `messages` 中注入。在第 5 轮的一条消息不会使第 5 轮之前的任何内容失效。

**不要在对话中途更改工具或模型。** 工具在位置 0 渲染；添加、删除或重新排序工具会使整个缓存失效。切换模型也是如此（缓存是按模型作用域的）。如果需要"模式"，不要交换工具集 —— 给 Claude 一个记录模式切换的工具，或者将模式作为消息内容传递。确定性地序列化工具（按名称排序）。

**分支操作必须重用父级的精确前缀。** 辅助计算（摘要、压缩、子代理）通常会发起一个单独的 API 调用。如果分支重新构建的 `system` / `tools` / `model` 有任何差异，它将完全错过父级的缓存。逐字复制父级的 `system`、`tools` 和 `model`，然后在末尾追加分支特有的内容。

## 静默失效因素

审查代码时，在任何输入到提示前缀的内容中搜索以下模式：

| 模式 | 为何破坏缓存 |
|---|---|
| 系统提示中的 `datetime.now()` / `Date.now()` / `time.time()` | 前缀每次请求都变化 |
| 内容早期的 `uuid4()` / `crypto.randomUUID()` / 请求 ID | 同上 —— 每次请求都是唯一的 |
| `json.dumps(d)` 未使用 `sort_keys=True` / 遍历 `set` | 非确定性序列化 → 前缀字节不同 |
| f-string 将会话/用户 ID 插值到系统提示中 | 每个用户一个前缀；无法跨用户共享 |
| 条件式系统部分（`if flag: system += ...`） | 每个标志组合都是一个不同的前缀 |
| `tools=build_tools(user)` 且集合因用户而异 | 工具在位置 0 渲染；无法跨用户缓存 |

解决方法：将动态部分移到最后一个断点之后，使其具有确定性，或者如果它不承担关键作用则将其删除。

## API 参考

```json
"cache_control": {"type": "ephemeral"}              // 5 分钟 TTL（默认）
"cache_control": {"type": "ephemeral", "ttl": "1h"} // 1 小时 TTL
```

- 每个请求最多 **4** 个 `cache_control` 断点。
- 可放置在任何内容块上：系统文本块、工具定义、消息内容块（`text`、`image`、`tool_use`、`tool_result`、`document`）。
- `messages.create()` 上的顶层 `cache_control` 会自动放置在最后一个可缓存块上 —— 当不需要精细放置时是最简单的方式。
- 最小可缓存前缀取决于模型。即使有标记，较短的前缀也会静默地不被缓存 —— 没有错误，只有 `cache_creation_input_tokens: 0`：

| 模型 | 最小值 |
|---|---:|
| Opus 4.8、Opus 4.7、Opus 4.6、Opus 4.5、Haiku 4.5 | 4096 个令牌 |
| Sonnet 4.6、Haiku 3.5、Haiku 3 | 2048 个令牌 |
| Sonnet 4.5、Sonnet 4.1、Sonnet 4、Sonnet 3.7 | 1024 个令牌 |

一个 3K 令牌的提示在 Sonnet 4.5 上可以缓存，但在 Opus 4.8 上会静默地不被缓存。

**经济学：** 缓存读取成本约为基础输入价格的 0.1 倍。缓存写入成本为 **5 分钟 TTL 1.25 倍，1 小时 TTL 2 倍**。盈亏平衡取决于 TTL：使用 5 分钟 TTL，两次请求即可盈亏平衡（1.25× + 0.1× = 1.35× 对比无缓存的 2×）；使用 1 小时 TTL，至少需要三次请求（2× + 0.2× = 2.2× 对比无缓存的 3×）。1 小时 TTL 可以在突发流量的间隙中保持条目存活，但加倍的写入成本意味着需要更多读取才能偿还。

## 验证缓存命中

响应中的 `usage` 对象报告缓存活动：

| 字段 | 含义 |
|---|---|
| `cache_creation_input_tokens` | 本次请求写入缓存的令牌数（您支付了约 1.25× 的写入溢价） |
| `cache_read_input_tokens` | 本次请求从缓存读取的令牌数（您支付了约 0.1×） |
| `input_tokens` | 按全价处理的令牌数（未缓存） |

如果在具有相同前缀的重复请求中 `cache_read_input_tokens` 为零，则说明存在静默失效因素 —— 比较两次请求之间渲染后的提示字节以找出原因。

**`input_tokens` 仅为未缓存的剩余部分。** 总提示大小 = `input_tokens + cache_creation_input_tokens + cache_read_input_tokens`。如果您的代理运行了数小时但 `input_tokens` 显示为 4K，则其余部分来自缓存 —— 请查看总和，而非单个字段。

各语言访问方式：`response.usage.cache_read_input_tokens`（Python/TS/Ruby）、`$message->usage->cacheReadInputTokens`（PHP）、`resp.Usage.CacheReadInputTokens`（Go/C#）、`.usage().cacheReadInputTokens()`（Java）。

## 失效层级

并非所有参数变化都会使一切失效。API 有三个缓存层级，变化仅会使其所在层级及以下层级失效：

| 变化 | 工具缓存 | 系统缓存 | 消息缓存 |
|---|---|:---:|:---:|:---:|
| 工具定义（添加/删除/重新排序） | ❌ | ❌ | ❌ |
| 模型切换 | ❌ | ❌ | ❌ |
| `speed`、网络搜索、引用开关 | ✅ | ❌ | ❌ |
| 系统提示内容 | ✅ | ❌ | ❌ |
| `tool_choice`、图片、`thinking` 启用/禁用 | ✅ | ✅ | ❌ |
| 消息内容 | ✅ | ✅ | ❌ |

含义：您可以按请求更改 `tool_choice` 或切换 `thinking`，而不会丢失工具+系统缓存。无需过度担心这些 —— 只有工具定义和模型变化才会强制完全重建。

## 20 个内容块的回溯窗口

每个断点最多向后查找 **20 个内容块**以找到先前的缓存条目。如果单轮对话添加了超过 20 个内容块（在包含许多 tool_use/tool_result 对的代理循环中很常见），下一个请求的断点将无法找到之前的缓存并静默地失效。

解决方法：在长轮次中每约 15 个内容块放置一个中间断点，或者将标记放在距离上一轮最后一个缓存块 20 个以内的块上。

---

## 并发请求时序

缓存条目只有在第一个响应**开始流式传输**后才可读取。N 个具有相同前缀的并行请求全部支付全价 —— 没有任何一个可以读取其他请求仍在写入的内容。

对于扇出模式：发送 1 个请求，等待第一个流式令牌（而非完整响应），然后发起剩余的 N−1 个请求。它们将读取第一个请求刚刚写入的缓存。
