# 文档协作编写工作流

此技能提供了一套结构化工作流，用于引导用户完成协作式文档创建。作为主动引导者，带领用户经历三个阶段：**上下文收集**、**优化与结构**和**读者测试**。

## 何时提供此工作流

**触发条件：**
- 用户提及编写文档："写一份文档"、"起草一份提案"、"创建一份规格"、"写下来"
- 用户提及特定文档类型："PRD"、"设计文档"、"决策文档"、"RFC"
- 用户似乎要开始一项重要的写作任务

**初始提议：**
向用户提供协作编写文档的结构化工作流。解释三个阶段：

1. **上下文收集**：用户提供所有相关上下文，同时 Claude 提出澄清性问题
2. **优化与结构**：通过头脑风暴和编辑，迭代构建每个章节
3. **读者测试**：用一个全新的 Claude（无上下文）测试文档，在他人阅读前发现盲点

解释这种方法有助于确保文档在他人阅读时效果良好（包括当他们将文档粘贴到 Claude 中时）。询问用户是否想尝试此工作流，或更倾向于自由写作。

如果用户拒绝，则自由写作。如果用户接受，进入阶段 1。

## 阶段 1：上下文收集

**目标：**缩小用户所知与 Claude 所知之间的差距，以便后续提供智能引导。

### 初始问题

首先询问用户有关文档的元上下文：

1. 这是什么类型的文档？（例如：技术规格、决策文档、提案）
2. 主要受众是谁？
3. 期望读者阅读后产生什么影响？
4. 是否有模板或特定格式需要遵循？
5. 还有其他约束条件或上下文需要了解吗？

告知他们可以用简写形式回答，或以最适合他们的方式倾倒信息。

**如果用户提供了模板或提到了文档类型：**
- 询问他们是否有模板文档可以分享
- 如果他们提供共享文档的链接，使用适当的集成来获取它
- 如果他们提供文件，则读取它

**如果用户提到要编辑现有的共享文档：**
- 使用适当的集成读取当前状态
- 检查没有 alt-text 的图片
- 如果存在没有 alt-text 的图片，解释当其他人使用 Claude 理解文档时，Claude 将无法看到它们。询问是否要生成 alt-text。如果是，请他们将每张图片粘贴到聊天中，以便生成描述性的 alt-text。

### 信息倾倒

一旦回答了初始问题，鼓励用户倾倒他们拥有的所有上下文。请求如下信息：
- 项目/问题的背景
- 相关团队讨论或共享文档
- 为什么不采用替代方案
- 组织上下文（团队动态、过往事件、人事情况）
- 时间压力或约束
- 技术架构或依赖关系
- 利益相关者关注点

建议他们不用担心组织整理——尽管全部倒出来。提供多种提供上下文的方式：
- 意识流式信息倾倒
- 指向要阅读的团队频道或线程
- 链接到共享文档

**如果集成了相关工具**（例如 Slack、Teams、Google Drive、SharePoint 或其他 MCP 服务器），说明可以使用这些工具直接拉取上下文。

**如果未检测到任何集成，且处于 Claude.ai 或 Claude 应用中：**建议他们可以在 Claude 设置中启用连接器，以便直接从消息应用和文档存储中拉取上下文。

告知他们在完成初始倾倒后，会提出澄清性问题。

**在上下文收集期间：**

- 如果用户提及团队频道或共享文档：
  - 如果集成可用：告知他们将立即读取内容，然后使用适当的集成
  - 如果集成不可用：说明无法访问。建议他们在 Claude 设置中启用连接器，或直接粘贴相关内容。

- 如果用户提及未知的实体/项目：
  - 询问是否应该搜索已连接的工具以了解更多信息
  - 等待用户确认后再搜索

- 随着用户提供上下文，跟踪已了解的内容和仍不清楚的内容

**提出澄清性问题：**

当用户表示已完成初始倾倒（或在提供大量上下文后），提出澄清性问题以确保理解：

根据上下文中的空白，生成 5-10 个编号问题。

告知他们可以用简写形式回答（例如，"1：是的，2：见 #channel，3：不，因为向后兼容"），链接到更多文档，指向要阅读的频道，或继续倾倒信息。以对他们最有效的方式为准。

**退出条件：**
当问题能显示出理解程度时——即可以在不需要解释基础知识的情况下询问边缘情况和权衡——说明已收集到足够的上下文。

**过渡：**
询问用户在此阶段是否还想提供更多上下文，或者是否该进入文档起草阶段。

如果用户想补充更多，让他们补充。准备就绪后，进入阶段 2。

## 阶段 2：优化与结构

**目标：**通过头脑风暴、筛选和迭代优化，逐节构建文档。

**向用户说明：**
解释文档将逐节构建。对于每个章节：
1. 将提出关于要包含哪些内容的澄清性问题
2. 将头脑风暴出 5-20 个选项
3. 用户将指示保留/删除/合并哪些内容
4. 将起草该章节
5. 将通过精确编辑进行优化

从最不确定的章节开始（通常是核心决策/提案），然后依次处理其余部分。

**章节排序：**

如果文档结构明确：
询问他们想从哪个章节开始。

建议从最不确定的章节开始。对于决策文档，通常是核心提案。对于规格文档，通常是技术方案。摘要章节最好留到最后。

如果用户不知道需要哪些章节：
根据文档类型和模板，为文档类型推荐 3-5 个合适的章节。

询问这个结构是否可行，或者是否需要调整。

**结构确定后：**

创建初始文档结构，所有章节使用占位文本。

**如果可以访问 artifacts：**
使用 `create_file` 创建一个 artifact。这为 Claude 和用户提供了一个可操作的基础框架。

告知他们将创建包含所有章节占位符的初始结构。

创建包含所有章节标题和简要占位文本（如 `[To be written]` 或 `[Content here]`）的 artifact。

提供 scaffold 链接，并说明是时候填充每个章节了。

**如果无法访问 artifacts：**
在工作目录中创建一个 markdown 文件。适当命名（例如 `decision-doc.md`、`technical-spec.md`）。

告知他们将创建包含所有章节占位符的初始结构。

创建包含所有章节标题和占位文本的文件。

确认文件名已创建，并说明是时候填充每个章节了。

**对于每个章节：**

### 步骤 1：澄清性问题

宣布将开始 [SECTION NAME] 章节的工作。提出 5-10 个关于应包含哪些内容的澄清性问题：

根据上下文和章节目的生成 5-10 个具体问题。

告知他们可以用简写形式回答，或直接指出哪些内容需要重点覆盖。

### 步骤 2：头脑风暴

对于 [SECTION NAME] 章节，根据章节复杂程度，头脑风暴 5-20 个可能包含的内容。寻找：
- 可能被遗忘的已共享上下文
- 尚未提及的角度或考量

根据章节复杂程度生成 5-20 个编号选项。最后，如果需要更多选项，可提供继续头脑风暴的机会。

### 步骤 3：筛选

询问哪些要点应保留、删除或合并。请求简短的理由说明，以帮助了解后续章节的优先级。

提供示例：
- "保留 1、4、7、9"
- "删除 3（与 1 重复）"
- "删除 6（受众已经知道这一点）"
- "合并 11 和 12"

**如果用户给出自由形式的反馈**（例如"看起来不错"或"我大部分认同，但是……"）而不是编号选择，提取他们的偏好并继续处理。解析他们希望保留/删除/更改的内容并加以应用。

### 步骤 4：缺口检查

根据他们选择的内容，询问 [SECTION NAME] 章节是否遗漏了任何重要内容。

### 步骤 5：起草

使用 `str_replace` 将该章节的占位文本替换为实际的草稿内容。

宣布现在将根据用户选择的内容起草 [SECTION NAME] 章节。

**如果使用 artifacts：**
起草后，提供 artifact 的链接。

请他们通读并指出需要修改的内容。注意，具体的反馈有助于后续章节的学习。

**如果使用文件（无 artifacts）：**
起草后，确认完成。

告知他们 [SECTION NAME] 章节已在 [filename] 中起草完成。请他们通读并指出需要修改的内容。注意，具体的反馈有助于后续章节的学习。

**给用户的关键说明（起草第一个章节时包含）：**
提供一条提示：不要直接编辑文档，而是请他们指出需要修改的内容。这有助于学习他们未来章节的风格。例如："删除 X 条——已在 Y 中涵盖"或"使第三段更简洁"。

### 步骤 6：迭代优化

当用户提供反馈时：
- 使用 `str_replace` 进行编辑（绝不重新打印整个文档）
- **如果使用 artifacts：**每次编辑后提供 artifact 链接
- **如果使用文件：**只需确认编辑完成
- 如果用户直接编辑文档并要求读取：在脑海中记下他们所做的更改，并在后续章节中记住这些更改（这显示了他们的偏好）

**持续迭代**直到用户对该章节满意为止。

### 质量检查

连续 3 次迭代没有实质性更改后，询问是否可以删除任何内容而不丢失重要信息。

章节完成后，确认 [SECTION NAME] 已完成。询问是否准备好进入下一个章节。

**对所有章节重复此过程。**

### 接近完成

当接近完成时（80% 以上的章节已完成），宣布将重新通读整个文档并检查：
- 各章节之间的流畅性和一致性
- 冗余或矛盾
- 任何感觉像"废话"或通用填充物的内容
- 是否每个句子都有分量

阅读整篇文档并提供反馈。

**当所有章节都起草并优化完毕：**
宣布所有章节已起草完成。表示将再通览一遍完整文档。

检查整体连贯性、流畅性和完整性。

提供任何最终建议。

询问是否准备好进入读者测试，或者是否还想优化其他内容。

## 阶段 3：读者测试

**目标：**用一个全新的 Claude（无上下文干扰）测试文档，验证其对读者是否有效。

**向用户说明：**
解释现在将进行测试，以确认文档对读者是否实际有效。这有助于发现盲点——那些对作者来说合理但可能让他人困惑的内容。

### 测试方法

**如果可以访问子代理（例如在 Claude Code 中）：**

直接执行测试，无需用户参与。

### 步骤 1：预测读者问题

宣布将预测读者在尝试查找此文档时可能会提出的问题。

生成 5-10 个读者实际会问的问题。

### 步骤 2：使用子代理测试

宣布将使用全新的 Claude 实例（无此对话的上下文）来测试这些问题。

对于每个问题，调用一个子代理，仅提供文档内容和该问题。

总结 Reader Claude 对每个问题的回答正确/错误情况。

### 步骤 3：执行额外检查

宣布将执行额外检查。

调用子代理检查歧义、错误假设和矛盾。

总结发现的任何问题。

### 步骤 4：报告与修复

如果发现问题：
报告 Reader Claude 在处理特定问题时存在困难。

列出具体问题。

表示将修复这些缺口。

对有问题的章节返回优化阶段。

---

**如果无法访问子代理（例如 claude.ai 网页界面）：**

用户需要手动进行测试。

### 步骤 1：预测读者问题

询问人们可能会提出什么问题来查找此文档。他们会向 Claude.ai 输入什么？

生成 5-10 个读者实际会问的问题。

### 步骤 2：设置测试

提供测试说明：
1. 打开一个新的 Claude 对话：https://claude.ai
2. 粘贴或分享文档内容（如果使用已启用连接器的共享文档平台，则提供链接）
3. 向 Reader Claude 提出已生成的问题

对于每个问题，指示 Reader Claude 提供：
- 答案
- 是否有任何内容存在歧义或不清晰
- 文档假设读者已具备哪些知识/上下文

检查 Reader Claude 是否给出正确答案或是否有任何误解。

### 步骤 3：额外检查

同时向 Reader Claude 提问：
- "这篇文档中哪些内容可能对读者造成歧义或不清晰？"
- "这篇文档假设读者已经具备哪些知识或背景？"
- "是否存在任何内部矛盾或不一致？"

### 步骤 4：根据结果迭代

询问 Reader Claude 在哪些问题上出错或存在困难。表示将修复这些缺口。

对有问题的章节返回优化阶段。

---

### 退出条件（两种方法通用）

当 Reader Claude 能持续正确回答问题，且不再发现新的缺口或歧义时，文档即可就绪。

## 最终审查

当读者测试通过后：
宣布文档已通过 Reader Claude 测试。在完成之前：

1. 建议他们自己进行最终通读——他们拥有这份文档并对其质量负责
2. 建议再次核对所有事实、链接或技术细节
3. 请他们确认文档达到了期望的影响效果

询问他们是否还需要一次审查，或者工作是否完成。

**如果用户想要最终审查，则提供。否则：**
宣布文档完成。提供几个最终提示：
- 考虑在附录中链接此对话，以便读者了解文档是如何开发的
- 使用附录在不使主文档臃肿的情况下提供深度内容
- 随着从真实读者收到反馈而更新文档

## 有效引导的技巧

**语气：**
- 直接且程序化
- 在影响用户行为时简要说明理由
- 不要试图"推销"这种方法——直接执行即可

**处理偏离：**
- 如果用户想跳过某个阶段：询问他们是跳过此阶段并自由写作
- 如果用户显得沮丧：承认这比预期花费了更长时间。建议加快速度的方法
- 始终让用户有权调整流程

**上下文管理：**
- 在整个过程中，如果缺少关于某个提及内容的上下文，主动询问
- 不要让缺口积累——在出现时立即处理

**Artifact 管理：**
- 使用 `create_file` 起草完整章节
- 使用 `str_replace` 进行所有编辑
- 每次更改后提供 artifact 链接
- 永远不要使用 artifacts 来列出头脑风暴内容——那只是对话

**质量重于速度：**
- 不要仓促完成各阶段
- 每次迭代应带来有意义的改进
- 目标是生成一份对读者真正有效的文档
