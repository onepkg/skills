# 技能创建器

一个用于创建新技能并迭代改进它们的技能。

总的来说，创建技能的过程如下：

- 确定您希望技能做什么以及大致应该如何做
- 编写技能草稿
- 创建一些测试提示并在 claude-with-access-to-the-skill 上运行它们
- 帮助用户定性和定量地评估结果
  - 当运行在后台进行时，如果没有定量评估则起草一些（如果已有一些，您可以按原样使用或修改如果您觉得需要更改）。然后向用户解释它们（或者如果它们已经存在，解释已经存在的那些）
  - 使用 `eval-viewer/generate_review.py` 脚本向用户显示结果供他们查看，并让他们查看定量指标
- 根据用户对结果评估的反馈重写技能（如果定量基准测试中出现明显缺陷也要修改）
- 重复直到您满意为止
- 扩大测试集并再次尝试更大规模

您在使用此技能时的工作是找出用户在此过程中的位置，然后介入并帮助他们通过这些阶段进展。例如，也许他们说"我想为 X 创建一个技能"。您可以帮助缩小他们的意思，编写草稿，编写测试用例，弄清楚他们如何想要评估，运行所有提示，并重复。

另一方面，也许他们已经有一个技能草稿。在这种情况下，您可以直接进入评估/迭代的循环部分。

当然，您应该始终保持灵活，如果用户说"我不需要运行一堆评估，只需与我一起感受"，您可以这样做。

然后在技能完成后（但顺序是灵活的），您还可以运行技能描述改进器，我们有一个单独的脚本来优化技能的触发。

酷吗？酷。

## 与用户沟通

技能创建器可能被各种熟悉程度的编程术语的人使用。如果您还没有听说过（您怎么可能知道，这只是最近才开始的），现在有一种趋势，Claude 的力量正在激励水管工打开他们的终端，父母和祖父母去谷歌搜索"如何安装 npm"。另一方面，大多数用户可能相当精通计算机。

所以请注意上下文线索来理解如何措辞您的沟通！在默认情况下，只是为了给您一些想法：

- "evaluation"和"benchmark"处于边缘，但可以接受
- 对于"JSON"和"assertion"，您需要看到用户的严重迹象表明他们知道这些是什么，然后才能在不解释的情况下使用它们

如果您有疑问，可以简要解释术语，如果您不确定用户是否会理解，可以随时用简短的定义澄清术语。

## 创建技能

### 捕获意图

首先了解用户的意图。当前对话可能已经包含用户想要捕获的工作流（例如，他们说"把这个变成技能"）。如果是这样，首先从对话历史中提取答案 — 使用的工具、步骤序列、用户所做的更正、观察到的输入/输出格式。用户可能需要填补空白，在进入下一步之前应该确认。

1. 这个技能应该使 Claude 能够做什么？
2. 这个技能何时应该触发？（什么用户短语/上下文）
3. 预期的输出格式是什么？
4. 我们应该设置测试用例来验证技能是否有效吗？具有客观可验证输出的技能（文件转换、数据提取、代码生成、固定工作流步骤）受益于测试用例。具有主观输出的技能（写作风格、艺术）通常不需要它们。根据技能类型建议适当的默认值，但让用户决定。

### 访谈和研究

主动询问边缘情况、输入/输出格式、示例文件、成功标准和依赖项的问题。在您完成这部分之前，等待编写测试提示。

检查可用的 MCP — 如果对研究有用（搜索文档、查找类似技能、查找最佳实践），如果可用则通过子代理并行研究，否则内联。准备好上下文以减轻用户的负担。

### 编写 SKILL.md

基于用户访谈，填写这些组件：

- **name**：技能标识符
- **description**：何时触发，它做什么。这是主要的触发机制 — 包括技能做什么 AND 何时使用它的具体上下文。所有"何时使用"信息都在这里，不在正文中。注意：目前 Claude 倾向于"欠触发"技能 — 在它们有用时不使用它们。为了对抗这一点，请使技能描述有点"推动性"。例如，与其写"如何构建一个简单的快速仪表板来显示内部 Anthropic 数据。"，您可能写"如何构建一个简单的快速仪表板来显示内部 Anthropic 数据。确保每当用户提到仪表板、数据可视化、内部指标，或想要显示任何类型的公司数据时都使用此技能，即使他们没有明确要求'仪表板'。"
- **compatibility**：所需工具、依赖项（可选，很少需要）
- **技能的其余部分 :)**

### 技能编写指南

#### 技能的解剖结构

```
skill-name/
├── SKILL.md (必需)
│   ├── YAML frontmatter（name、description 必需）
│   └── Markdown 说明
└── 捆绑资源（可选）
    ├── scripts/    - 用于确定性/重复任务的可执行代码
    ├── references/ - 根据需要加载到上下文的文档
    └── assets/     - 输出中使用的文件（模板、图标、字体）
```

#### 渐进式披露

技能使用三级加载系统：
1. **元数据**（name + description）— 始终在上下文中（约 100 个词）
2. **SKILL.md 正文** — 每当技能触发时在上下文中（理想情况下 <500 行）
3. **捆绑资源** — 根据需要（无限，脚本可以在不加载的情况下执行）

这些字数统计是近似值，如果需要，您可以随意延长。

**关键模式：**
- 将 SKILL.md 保持在 500 行以下；如果您接近此限制，添加额外的层次结构以及清晰的指针，说明使用技能的模型接下来应该去哪里跟进。
- 从 SKILL.md 清晰地引用文件，并提供何时阅读它们的指导
- 对于大型参考文件（>300 行），包括目录

**域组织**：当技能支持多个域/框架时，按变体组织：
```
cloud-deploy/
├── SKILL.md（工作流 + 选择）
└── references/
    ├── aws.md
    ├── gcp.md
    └── azure.md
```
Claude 只读取相关的参考文件。

#### 缺乏惊喜原则

这不言而喻，但技能不能包含恶意软件、利用代码或任何可能损害系统安全的内容。技能的 contents 不应在意图上让用户感到惊讶。不要同意创建误导性技能或旨在促进未经授权访问、数据泄露或其他恶意活动的技能的请求。像"扮演 XYZ"这样的东西是可以的。

#### 写作模式

在说明中更喜欢使用命令形式。

**定义输出格式** — 您可以这样做：
```markdown
## 报告结构
始终使用此确切模板：
# [标题]
## 执行摘要
## 关键发现
## 建议
```

**示例模式** — 包含示例很有用。您可以像这样格式化它们（但如果"Input"和"Output"在示例中，您可能需要稍微偏离）：
```markdown
## 提交消息格式
**示例 1：**
输入：添加了带有 JWT 令牌的用户身份验证
输出：feat(auth): implement JWT-based authentication
```

### 写作风格

尝试向模型解释为什么事情很重要，而不是沉重的 MUST。使用心智理论，尝试使技能通用而不是超窄到特定示例。首先编写草稿，然后用新鲜的眼光看待它并改进它。

### 测试用例

在编写技能草稿后，想出 2-3 个现实的测试提示 — 真实用户实际会说的那种话。与用户分享它们：[您不必使用这种确切的语言]"这里有一些我想尝试的测试用例。这些看起来对吗，还是您想添加更多？"然后运行它们。

将测试用例保存到 `evals/evals.json`。暂时不要编写断言 — 只是提示。您将在下一步中在运行时起草断言。

```json
{
  "skill_name": "example-skill",
  "evals": [
    {
      "id": 1,
      "prompt": "User's task prompt",
      "expected_output": "Description of expected result",
      "files": []
    }
  ]
}
```

有关完整模式（包括您稍后将添加的 `assertions` 字段），请参阅 `references/schemas.md`。

## 运行和评估测试用例

本节是一个连续的序列 — 不要中途停止。不要使用 `/skill-test` 或任何其他测试技能。

将结果放在 `<skill-name>-workspace/` 中作为技能目录的同级。在工作区内，按迭代组织结果（`iteration-1/`、`iteration-2/` 等），在其中，每个测试用例获得一个目录（`eval-0/`、`eval-1/` 等）。不要预先创建所有这些 — 只需在您进行时创建目录。

### 步骤 1：在同一轮中生成所有运行（with-skill 和 baseline）

对于每个测试用例，在同一轮中生成两个子代理 — 一个带技能，一个不带。这很重要：不要先生成 with-skill 运行，然后再回来处理 baselines。一次性启动所有内容，以便它们都在同一时间附近完成。

**With-skill 运行：**

```
Execute this task:
- Skill path: <path-to-skill>
- Task: <eval prompt>
- Input files: <eval files if any, or "none">
- Save outputs to: <workspace>/iteration-<N>/eval-<ID>/with_skill/outputs/
- Outputs to save: <what the user cares about — e.g., "the .docx file", "the final CSV">
```

**Baseline 运行**（相同的提示，但 baseline 取决于上下文）：
- **创建新技能**：完全没有技能。相同的提示，没有技能路径，保存到 `without_skill/outputs/`。
- **改进现有技能**：旧版本。在编辑之前，快照技能（`cp -r <skill-path> <workspace>/skill-snapshot/`），然后将 baseline 子代理指向快照。保存到 `old_skill/outputs/`。

为每个测试用例编写一个 `eval_metadata.json`（断言现在可以为空）。根据其测试的内容给每个 eval 一个描述性名称 — 不仅仅是"eval-0"。也为此名称使用目录。如果此迭代使用新的或修改的 eval 提示，为每个新的 eval 目录创建这些文件 — 不要假设它们从以前的迭代中继承。

```json
{
  "eval_id": 0,
  "eval_name": "descriptive-name-here",
  "prompt": "The user's task prompt",
  "assertions": []
}
```

### 步骤 2：当运行时在进行中时，起草断言

不要只是等待运行完成 — 您可以富有成效地使用这段时间。为每个测试用例起草定量断言并向用户解释它们。如果 `evals/evals.json` 中已经存在断言，审查它们并解释它们检查什么。

好的断言是客观可验证的并具有描述性名称 — 它们应该在基准测试查看器中清晰可读，以便浏览结果的人立即理解每个断言检查什么。主观技能（写作风格、设计质量）最好定性评估 — 不要将断言强加于需要人类判断的事情上。

起草断言后，更新 `eval_metadata.json` 文件和 `evals/evals.json`。还向用户解释他们将在查看器中看到什么 — 定性输出和定量基准测试。

### 步骤 3：当运行完成时，捕获计时数据

当每个子代理任务完成时，您会收到包含 `total_tokens` 和 `duration_ms` 的通知。立即将此数据保存到运行目录中的 `timing.json`：

```json
{
  "total_tokens": 84852,
  "duration_ms": 23332,
  "total_duration_seconds": 23.3
}
```

这是捕获此数据的唯一机会 — 它通过任务通知传入，不会持久化到其他任何地方。在每个通知到达时处理它们，而不是尝试批量处理它们。

### 步骤 4：评分、聚合和启动查看器

一旦所有运行完成：

1. **评分每个运行** — 生成分数子代理（或内联评分），读取 `agents/grader.md` 并根据输出评估每个断言。将结果保存到每个运行目录中的 `grading.json`。grading.json expectations 数组必须使用字段 `text`、`passed` 和 `evidence`（不是 `name`/`met`/`details` 或其他变体）— 查看器依赖于这些确切的字段名称。对于可以以编程方式检查的断言，编写并运行脚本而不是目视检查 — 脚本更快、更可靠，并且可以在迭代之间重用。

2. **聚合到基准测试** — 从技能创建器目录运行聚合脚本：
   ```bash
   python -m scripts.aggregate_benchmark <workspace>/iteration-N --skill-name <name>
   ```
   这会生成 `benchmark.json` 和 `benchmark.md`，其中包含每个配置的 pass_rate、time 和 tokens，带有 mean ± stddev 和 delta。如果手动生成 benchmark.json，请参阅 `references/schemas.md` 获取查看器期望的确切模式。
将每个 with_skill 版本放在其 baseline 对应项之前。

3. **进行分析员传递** — 读取基准测试数据并揭示聚合统计可能隐藏的图案。请参阅 `agents/analyzer.md`（"分析基准测试结果"部分）了解要查找的内容 — 例如无论技能如何总是通过的断言（非区分）、高方差评估（可能不稳定）和时间/令牌权衡。

4. **启动查看器**，同时包含定性输出和定量数据：
   ```bash
   nohup python <skill-creator-path>/eval-viewer/generate_review.py \
     <workspace>/iteration-N \
     --skill-name "my-skill" \
     --benchmark <workspace>/iteration-N/benchmark.json \
     > /dev/null 2>&1 &
   VIEWER_PID=$!
   ```
   对于第 2+ 次迭代，还要传递 `--previous-workspace <workspace>/iteration-<N-1>`。

   **Cowork / headless 环境：** 如果 `webbrowser.open()` 不可用或环境没有显示，使用 `--static <output_path>` 写入独立的 HTML 文件而不是启动服务器。当用户点击"Submit All Reviews"时，反馈将作为 `feedback.json` 文件下载。下载后，将 `feedback.json` 复制到工作区目录以供下一次迭代拾取。

注意：请使用 generate_review.py 创建查看器；无需编写自定义 HTML。

5. **告诉用户**类似："我已在您的浏览器中打开结果。有两个选项卡 — 'Outputs' 让您单击浏览每个测试用例并留下反馈，'Benchmark' 显示定量比较。完成后，回到这里告诉我。"

### 用户在查看器中看到的内容

"Outputs"选项卡一次显示一个测试用例：
- **Prompt**：给出的任务
- **Output**：技能生成的文件，在可能的情况下内联渲染
- **Previous Output**（第 2+ 次迭代）：折叠部分显示上次迭代的输出
- **Formal Grades**（如果运行了评分）：折叠部分显示断言通过/失败
- **Feedback**：文本框在他们键入时自动保存
- **Previous Feedback**（第 2+ 次迭代）：他们上次的评论，显示在文本框下方

"Benchmark"选项卡显示统计摘要：每个配置的通过率、时间和令牌使用量，带有每次评估的细分和分析员观察。

导航通过 prev/next 按钮或箭头键。完成后，他们点击"Submit All Reviews"，将所有反馈保存到 `feedback.json`。

### 步骤 5：读取反馈

当用户告诉您他们完成时，读取 `feedback.json`：

```json
{
  "reviews": [
    {"run_id": "eval-0-with_skill", "feedback": "the chart is missing axis labels", "timestamp": "..."},
    {"run_id": "eval-1-with_skill", "feedback": "", "timestamp": "..."},
    {"run_id": "eval-2-with_skill", "feedback": "perfect, love this", "timestamp": "..."}
  ],
  "status": "complete"
}
```

空反馈意味着用户认为它很好。专注于用户有具体抱怨的测试用例的改进。

完成后杀死查看器服务器：

```bash
kill $VIEWER_PID 2>/dev/null
```

## 改进技能

这是循环的核心。您已经运行了测试用例，用户已经审查了结果，现在您需要根据他们的反馈使技能更好。

### 如何思考改进

1. **从反馈中概括。** 这里发生的大图景是我们试图创建可以在许多不同提示中使用一百万次（可能是字面意思，甚至更多谁知道）的技能。在这里，您和用户反复迭代只有几个示例，因为它有助于更快地移动。用户深入了解这些示例，对他们来说评估新输出很快。但是，如果您和用户共同开发的技能仅适用于这些示例，它是无用的。与其放入繁琐的过度拟合更改或压迫性的限制性 MUST，如果有一些顽固的问题，您可以尝试分支并使用不同的隐喻，或推荐不同的工作模式。尝试相对便宜，也许您会遇到很棒的东西。

2. **保持提示简洁。** 删除没有发挥作用的東西。确保阅读转录本，而不仅仅是最终输出 — 如果看起来技能使模型浪费大量时间做无生产力的事情，您可以尝试摆脱使它们这样做的技能部分，看看会发生什么。

3. **解释原因。** 努力解释要求模型做的每件事背后的**原因**。今天的 LLM 很*聪明*。它们有良好的心智理论，当给予良好的 harness 时，可以超越死板的指令，真正实现目标。即使用户的反馈简洁或沮丧，也要尝试真正理解任务和用户为什么写他们写的东西，以及他们实际写了什么，然后将这种理解转化为说明。如果您发现自己用大写写 ALWAYS 或 NEVER，或使用超级 rigid 结构，那是一个黄色标志 — 如果可能，重新框架并解释推理，以便模型理解您要求的事情为什么重要。这是一种更人性化、更强大、更有效的方法。

4. **寻找测试用例之间的重复工作。** 阅读测试运行的转录本，并注意子代理是否都独立编写了类似的助手脚本或采取了相同的多步骤方法。如果所有 3 个测试用例都导致子代理编写 `create_docx.py` 或 `build_chart.py`，这是一个强烈的信号，表明技能应该捆绑该脚本。编写一次，将其放在 `scripts/` 中，并告诉技能使用它。这节省了每次未来调用重新发明轮子。

这项任务非常重要（我们试图在这里创造每年数十亿美元的经济价值！），您的思考时间不是瓶颈；花时间仔细考虑。我建议编写修订草稿，然后重新审视并进行改进。真正尽最大努力进入用户的头脑，了解他们想要和需要什么。

### 迭代循环

在改进技能后：

1. 将您的改进应用到技能
2. 将所有测试用例重新运行到新的 `iteration-<N+1>/` 目录中，包括 baseline 运行。如果您正在创建新技能，baseline 始终是 `without_skill`（没有技能）— 这在迭代之间保持不变。如果您正在改进现有技能，根据您的判断决定什么作为 baseline 有意义：用户带来的原始版本，或前一次迭代。
3. 使用 `--previous-workspace` 指向前一次迭代启动查看器
4. 等待用户审查并告诉您他们完成
5. 读取新的反馈，再次改进，重复

继续直到：
- 用户说他们满意
- 反馈都是空的（一切看起来都很好）
- 您没有取得有意义的进展

## 高级：盲比较

对于您想要对两个版本的技能进行更严格比较的情况（例如，用户问"新版本真的更好吗？"），有一个盲比较系统。阅读 `agents/comparator.md` 和 `agents/analyzer.md` 获取详细信息。基本思想是：给两个输出给一个独立的代理而不告诉它哪个是哪个，让它判断质量。然后分析为什么赢家赢了。

这是可选的，需要子代理，大多数用户不需要它。人工审查循环通常就足够了。

## 描述优化

SKILL.md frontmatter 中的 description 字段是决定 Claude 是否调用技能的主要机制。在创建或改进技能后，提供优化描述以提高触发准确性。

### 步骤 1：生成触发评估查询

创建 20 个评估查询 — should-trigger 和 should-not-trigger 的混合。保存为 JSON：

```json
[
  {"query": "the user prompt", "should_trigger": true},
  {"query": "another prompt", "should_trigger": false}
]
```

查询必须是真实的，是 Claude Code 或 Claude.ai 用户实际会输入的东西。不是抽象的请求，而是具体和特定的请求，并有足够的细节。例如，文件路径、关于用户工作或情况的个人上下文、列名和值、公司名称、URL。一些背景故事。有些可能是小写的或包含缩写或拼写错误或非正式语言。使用不同长度的混合，并专注于边缘情况而不是使它们明确（用户将有机会签署它们）。

不好：`"Format this data"`、`"Extract text from PDF"`、`"Create a chart"`

好：`"ok so my boss just sent me this xlsx file (its in my downloads, called something like 'Q4 sales final FINAL v2.xlsx') and she wants me to add a column that shows the profit margin as a percentage. The revenue is in column C and costs are in column D i think"`

对于 **should-trigger** 查询（8-10 个），考虑覆盖范围。您需要相同意图的不同措辞 — 一些正式，一些随意。包括用户没有明确命名技能或文件类型但显然需要它的情况。加入一些不常见的用例和此技能与其他技能竞争但应该赢的情况。

对于 **should-not-trigger** 查询（8-10 个），最有价值的是接近未命中 — 与技能共享关键字或概念但实际上需要其他东西的查询。考虑相邻域、模糊措辞，其中天真的关键字匹配会触发但不应该，以及查询触及技能做的事情但在另一个工具更合适的上下文中。

要避免的关键事情：不要使 should-not-trigger 查询明显无关。"Write a fibonacci function"作为 PDF 技能的负面测试太容易了 — 它没有测试任何东西。负面情况应该真正棘手。

### 步骤 2：与用户审查

使用 HTML 模板向用户展示评估集进行审查：

1. 从 `assets/eval_review.html` 读取模板
2. 替换占位符：
   - `__EVAL_DATA_PLACEHOLDER__` → 评估项目的 JSON 数组（周围没有引号 — 它是 JS 变量赋值）
   - `__SKILL_NAME_PLACEHOLDER__` → 技能的名称
   - `__SKILL_DESCRIPTION_PLACEHOLDER__` → 技能的当前描述
3. 写入临时文件（例如，`/tmp/eval_review_<skill-name>.html`）并打开它：`open /tmp/eval_review_<skill-name>.html`
4. 用户可以编辑查询、切换 should-trigger、添加/删除条目，然后点击"Export Eval Set"
5. 文件下载到 `~/Downloads/eval_set.json` — 检查 Downloads 文件夹中的最新版本，以防有多个（例如，`eval_set (1).json`）

这一步很重要 — 糟糕的评估查询会导致糟糕的描述。

### 步骤 3：运行优化循环

告诉用户："这需要一些时间 — 我将在后台运行优化循环并定期检查它。"

将评估集保存到工作区，然后在后台运行：

```bash
python -m scripts.run_loop \
  --eval-set <path-to-trigger-eval.json> \
  --skill-path <path-to-skill> \
  --model <model-id-powering-this-session> \
  --max-iterations 5 \
  --verbose
```

使用系统提示中的模型 ID（为当前会话提供动力的那个），以便触发测试与用户实际体验的匹配。

当它运行时，定期 tail 输出以向用户提供关于它在哪个迭代以及分数看起来如何的更新。

这自动处理完整的优化循环。它将评估集拆分为 60% 训练和 40% 保留测试，评估当前描述（运行每个查询 3 次以获得可靠的触发率），然后调用 Claude 根据失败的内容提出改进。它在训练和测试上重新评估每个新描述，迭代最多 5 次。完成后，它在浏览器中打开一个 HTML 报告显示每次迭代的结果，并返回带有 `best_description` 的 JSON — 由测试分数而不是训练分数选择以避免过拟合。

### 技能触发如何工作

理解触发机制有助于设计更好的评估查询。技能出现在 Claude 的 `available_skills` 列表中，带有它们的 name + description，Claude 根据该描述决定是否咨询技能。重要的是要知道 Claude 只为它不能轻易自己处理的任务咨询技能 — 简单的单步查询如"read this PDF"可能不会触发技能，即使描述完全匹配，因为 Claude 可以直接使用基本工具处理它们。复杂、多步或专门的查询在描述匹配时可靠地触发技能。

这意味着您的评估查询应该足够实质性，以至于 Claude 实际上会从咨询技能中受益。像"read file X"这样的简单查询是糟糕的测试用例 — 无论描述质量如何，它们都不会触发技能。

### 步骤 4：应用结果

从 JSON 输出中获取 `best_description` 并更新技能的 SKILL.md frontmatter。向用户显示前后并报告分数。

### 打包和呈现（仅在 `present_files` 工具可用时）

检查您是否可以访问 `present_files` 工具。如果没有，跳过此步骤。如果有，打包技能并将 .skill 文件呈现给用户：

```bash
python -m scripts.package_skill <path/to/skill-folder>
```

打包后，将用户定向到生成的 `.skill` 文件路径，以便他们可以安装它。

## Claude.ai 特定说明

在 Claude.ai 中，核心工作流是相同的（草稿 → 测试 → 审查 → 改进 → 重复），但因为 Claude.ai 没有子代理，一些机制会改变。以下是需要适应的内容：

**运行测试用例**：没有子代理意味着没有并行执行。对于每个测试用例，读取技能的 SKILL.md，然后遵循其说明自己完成测试提示。一个一个地做。这不如独立的子代理严格（您编写了技能并且您也在运行它，所以您有完整的上下文），但它是一个有用的健全性检查 — 人工审查步骤可以补偿。跳过 baseline 运行 — 只需使用技能按要求完成任务。

**审查结果**：如果您无法打开浏览器（例如，Claude.ai 的 VM 没有显示，或者您在远程服务器上），完全跳过浏览器查看器。相反，直接在对话中呈现结果。对于每个测试用例，显示提示和输出。如果输出是用户需要看到的文件（如 .docx 或 .xlsx），将其保存到文件系统并告诉他们它在哪里，以便他们可以下载和检查。内联询问反馈："这看起来怎么样？您想改变什么吗？"

**基准测试**：跳过量化的基准测试 — 它依赖于 baseline 比较，在没有子代理的情况下没有意义。专注于来自用户的定性反馈。

**迭代循环**：与以前相同 — 改进技能，重新运行测试用例，询问反馈 — 只是中间没有浏览器查看器。如果您有文件系统，您仍然可以将结果组织到迭代目录中。

**描述优化**：此部分需要 `claude` CLI 工具（特别是 `claude -p`），仅在 Claude Code 中可用。如果您在 Claude.ai 上，请跳过它。

**盲比较**：需要子代理。跳过它。

**打包**：`package_skill.py` 脚本在任何有 Python 和文件系统的地方工作。在 Claude.ai 上，您可以运行它，用户可以下载生成的 `.skill` 文件。

**更新现有技能**：用户可能要求您更新现有技能，而不是创建新技能。在这种情况下：
- **保留原始名称。** 注意技能的目录名称和 `name` frontmatter 字段 — 不变地使用它们。例如，如果安装的技能是 `research-helper`，输出 `research-helper.skill`（不是 `research-helper-v2`）。
- **在编辑之前复制到可写位置。** 已安装的技能路径可能是只读的。复制到 `/tmp/skill-name/`，在那里编辑，并从副本打包。
- **如果手动打包，先在 `/tmp/` 中暂存**，然后复制到输出目录 — 直接写入可能因权限而失败。

## Cowork 特定说明

如果您在 Cowork 中，主要需要了解的是：

- 您有子代理，所以主要工作流（并行生成测试用例、运行 baselines、评分等）都有效。（但是，如果您遇到严重的超时问题，可以串行而不是并行运行测试提示。）
- 您没有浏览器或显示，所以在生成评估查看器时，使用 `--static <output_path>` 写入独立的 HTML 文件而不是启动服务器。然后提供一个链接，用户可以点击在他们的浏览器中打开 HTML。
- 由于某种原因，Cowork 设置似乎使 Claude 不愿意在运行测试后生成评估查看器，所以重申一下：无论您在 Cowork 还是在 Claude Code 中，在运行测试后，您都应该始终生成评估查看器供人类在亲自修订技能并尝试进行更正之前查看示例，使用 `generate_review.py`（不编写您自己的精品 html 代码）。提前抱歉，但我要用大写强调：在亲自评估输入*之前*生成评估查看器。您希望尽快将它们放在人类面前！
- 反馈工作方式不同：因为没有运行的服务器，查看器的"Submit All Reviews"按钮将下载 `feedback.json` 作为文件。然后您可以从那里读取它（您可能必须先请求访问）。
- 打包有效 — `package_skill.py` 只需要 Python 和文件系统。
- 描述优化（`run_loop.py` / `run_eval.py`）应该在 Cowork 中正常工作，因为它通过 subprocess 使用 `claude -p`，而不是浏览器，但请等到您完全完成制作技能并且用户同意它处于良好状态后再进行。
- **更新现有技能**：用户可能要求您更新现有技能，而不是创建新技能。遵循上面 claude.ai 部分中的更新指导。
